# 严格工作流引擎

本文维护首期状态、证据与信任边界；业务演练见 ../../examples/workflow-sandbox/。流程技能指导代理，内核维护权威状态，宿主钩子仅展示状态。

## 首期能力与限制

首期实现本地完成门禁，不实现所有工具防绕过。相同操作系统用户仍可修改状态库、检查程序和运行环境，不将本地交互终端确认称为可信身份认证。完整档批准与标准/完整档评审没有可信签署渠道时保持缺项，不让代理自行填充。
首期机器阶段使用 planning、verification、done；状态使用 created、ready、running、passed、failed、stale、completed、cancelled。实施工作由代理完成，尚不纳管为独立机器阶段；阻塞通过 missing 与结构化错误表达，不伪称已有完整阶段调度。检查计划和任务都有版本；技能加载、自然语言成功和度量记录不是有效证据。

## 使用

默认保持提醒模式。项目配置显式添加 engine.enabled: true（两层 YAML 映射）后启用 Codex 状态适配，以 WORKFLOW_TASK_ID 环境变量绑定当前任务；首期没有持久化会话绑定表，需每个会话显式设置。绑定只选择任务，不提供权限。
CLI：`python3 plugins/workflow-core/scripts/workflow_engine_cli.py --root PROJECT status --task ID`。
创建须提供档位、验收 ID 和 JSON 检查计划；修改请求须提供版本与请求 ID。相同请求重放不得重复推进，相同 ID 不同参数必须拒绝。
检查计划须人工在独立交互终端审阅并确认摘要后执行；不提供免交互 --yes，确认不代表业务方案批准。

## 检查计划

JSON 顶层为 version=1 与 checks。每项含 id、argv（非空字符串数组）、cwd（项目内相对目录）、timeout（正秒数）、covers（format/analyze/test）和 acceptance（验收 ID）。不执行 shell 字符串，不从 PASS 文本推测成功。
格式、分析和测试是最低必需覆盖，不能省略；项目必须选择真正检查对应目标的命令。退出零只能证明受信检查程序成功执行，不能证明测试质量或零测试被发现，检查包装器应拒绝空覆盖。

## 状态与生命周期

SQLite 状态在本机用户数据目录，禁止放在纳管工作区中。写入使用事务和任务版本；外部子进程运行期间不持有写事务。检查前后核对内容指纹，完成前再次核对；输入变化导致证据过期。状态查询在发现已完成任务变更时撤销有效完成状态，非后台持续文件监控。
纳管内容不能只使用 HEAD、文件大小或 mtime。符号链接、子模块、无法安全读取的输入需要显式受阻。忽略生成缓存不等于允许忽略任意业务输入。敏感文件不进入正文日志，无法安全纳管时停止。
执行输出不持久化，记录退出码与受控原因；超时终止进程组。进程退出后未完成记录需恢复核对，不能自动当作成功。

## 后续阶段

第二期研究实际宿主可拦截能力与可信人工批准；第三期处理跨进程协调和外部写入核对；第四期再扩展任务图和增量观测。不将首期状态提示描述为已阻止所有文件修改。
