# PRD 拆解与追溯

下文的 `${CLAUDE_PLUGIN_ROOT}` 指当前技能所在的插件根目录。如果它没有被替换成绝对路径（如在 Codex 中），从已加载的 `SKILL.md` 路径向上三级定位，执行命令时直接代入绝对路径。

把外部需求同步为仓库产品文档、拆成可独立验收的子需求，并持续对照设计、工程规范、技术规格和验收证据。路径取自项目「工作流配置」的 `docs.product_root`（下文简称 `product/`，默认 `docs/product/`）。

需求、卡和规格的用词以术语表（`docs.glossary`）为准；PRD 里出现表中没有、含糊或一词多义的业务词时，列为“术语待确认”并给出建议定义，用户确认后写入术语表，不擅自定义。

**缺文档时按需生成**：
- 需求说明、版本任务总览、项目首页不存在：说明项目还没初始化，建议先加载 `init` 技能；用户要求直接开始时，只从 `${CLAUDE_PLUGIN_ROOT}/templates/docs/product/` 补建本次要写的那几个文件。
- **模块卡**在首次拆出某个模块时创建：`product/任务/<模块>.md`，一级标题为模块名，子需求按 `${CLAUDE_PLUGIN_ROOT}/templates/task-card.md` 填写，并在版本任务总览加一行入口。已有模块卡则追加子需求，不另建文件。
- 只创建缺失文件，不覆盖已有内容。

## 1. 先明确授权

本轮是只同步文档、拆分任务、写提案还是实施？只做指定范围。检查工作区与文档基线，保护已有修改。

## 2. 对照依据（拆解和开工前都要核对）

1. **需求来源**：原文版本、日期、章节、链接、本地同步范围。图片和未读取的链接不算已核对。
2. **产品文档**：需求说明、版本任务总览、相关模块卡、已确认决定与延期范围。
3. **设计**：权威文件、页面/节点、交互与异常状态；多个来源冲突先记录再请求确认。
4. **工程规范**：工作流、代码、架构、UI、接口、测试；已有基础设施和限制要反映到任务。
5. **技术现状**：相关源码、测试、主规格、进行中变更；区分已实现、目标需求、建议设计和待确认假设。
6. **验收记录**：实际测试、联调、人工验收和未覆盖项，对应的代码及契约版本。

需求与工程约束冲突时记录具体条目、影响和待决定人，**不静默选一方**。没有负责人写“待指定”，不编造姓名或批准结论。

## 3. 文档职责（同一事实只维护一处）

| 文档 | 维护 | 不维护 |
| --- | --- | --- |
| 需求说明 | 产品目标、范围、业务规则、待确认问题、已确认决定与依据 | 拆分进度、认领、实施流水、技术勾选 |
| 设计索引 | 设计文件地址、页面/节点定位、主稿确认依据、读取范围、设计差异、业务关联 | 任务完成状态、接口契约、技术清单 |
| 模块任务卡 | 可独立验收的目标、来源引用、差距、范围、依赖、验收、负责人、产品状态与证据 | 复制整份需求、设计索引或技术 tasks |
| 版本任务总览 | 模块分组、优先级、依赖顺序、模块卡入口 | 与模块卡竞争的完成清单 |
| 技术规格/设计/tasks | 行为契约、技术取舍、唯一技术任务清单 | 产品验收结论 |
| 交接记录 | 授权范围、工作区快照、进度引用、阻塞、下一步 | 第二份需求、任务清单或批准记录 |

## 4. 接收与同步步骤

1. 记录需求版本、提供日期、来源和同步方式；说明是逐字备份还是结构化整理。整理**不得悄悄删除**数值边界、异常流程、延期标识或冲突。
2. 列出业务模块、核心模型、状态流转、角色、权限、接口与非功能要求。重复章节用标题和规则内容定位，不只靠编号。
3. 同步登记 UI 设计来源：文件链接/标识、页面、可定位节点、版本或核对日期、确认依据、读取范围。一个页面覆盖多项业务时先登记共享页面。
4. 标注“已核对 / 仅同步文字 / 图片待核对 / 外部来源不可读”；无法访问不等于没有需求。
5. 差异按下文「缺失与冲突」登记；可独立的内容继续，关键契约不明时停止依赖实现。

## 5. 子需求拆分

按**可独立验收的业务结果**拆分，不只按页面或“前端/后端/测试”拆。每项写明（字段模板见 `${CLAUDE_PLUGIN_ROOT}/templates/task-card.md`）：

- 稳定编号、标题、目标、首期/延期、优先级、状态
- 原文版本与章节、本地需求链接、相关设计与规范链接
- 当前实现与差距、范围与非目标、接口/数据/其他卡依赖
- 验收场景：成功、空状态、业务拒绝、边界、异常、恢复、适用平台
- 待确认问题、负责人或待指定、阻塞范围与恢复条件
- 关联技术变更/Issue 与验证记录；未建立写“未建立”，不放假链接

同一业务能力只选一个归属卡，其他卡引用。在总览或卡内维护简短对照：来源章节 → 本地需求章节 → 任务编号 → 规范/设计 → 差异/核对状态。

## 6. UI 关联与整页交付

| 阶段 | UI 工作 | 结果 |
| --- | --- | --- |
| PRD 解析 | 登记设计文件、版本、页面清单；区分视觉稿/原型/流程白板；注明读取范围 | 来源已登记，未读取不标已核对 |
| 子需求拆分 | 建“页面/状态 → 设计节点 → 子需求”映射；整页被多项复用时建共享 UI 项（如 `<模块>-UIxx`） | 设计索引存映射，模块卡存共享 UI 状态，业务卡引用 |
| 方案前核对 | 读所选节点，比对截图、文字、交互、素材，确认同名稿的主稿；记录缺失状态与 PRD 差异 | 所选范围有可追溯依据 |
| 方案设计 | 共用组件、布局/适配、状态与交互边界、素材处理、分批接入方式 | 标准档写卡内计划，完整档写 design/tasks |
| 实施 | 先做布局与展示状态，再接业务行为 | 未接入的操作不得给出“成功”反馈 |
| 验收 | 视觉还原、适配、业务交互分别验证 | 共享 UI 与各子需求分别留证据 |

- 文件链接 ≠ 节点已读；结构/文字已读 ≠ 截图、素材、交互已确认。
- 同名多稿不按节点编号或画板顺序猜新旧。
- Toast、加载、确认弹窗、空/错占位等跨页面基础组件登记为基础模块的共享 UI 项，不挂在首个使用它的业务模块下。
- 设计未给出的加载、禁用、错误、空态、返回行为及窄屏、大字体、键盘、深色等场景，按工程规范补充并标明依据，不伪装成设计原值。
- 具体设计工具的读取方法见对应 `design-*` 插件。

## 7. 缺失与冲突

| 情况 | 动作 | 可继续范围 |
| --- | --- | --- |
| 缺链接、章节、设计文件或节点 | 先在仓库和可用连接中查；找不到就在模块卡标记缺项 | 无依赖的拆分/调查 |
| 同名多稿、来源冲突、主稿未选 | 在设计索引列出候选、差异、既有确认依据，请决定人确认 | 对照、方案草拟 |
| 只读到结构/文字 | 标记实际读取范围；工具不可用记录限制 | 文字/结构分析 |
| 关键业务规则、接口或批准缺失 | 业务问题登记到需求说明「待确认问题」，接口问题登记到变更或卡 | 只暂停依赖部分 |
| 文档、源码、状态、证据不一致 | 保留差异，核对版本，必要时重跑最小验证 | 不受影响部分 |

模块卡中的缺项统一格式：

```text
- 待确认：<具体缺项或冲突>｜影响：<阻塞的子需求/步骤>｜负责人：<姓名或待指定>｜恢复条件：<取得什么后继续>｜来源：<问题编号、设计小节或变更链接>
```

## 8. 变更同步与状态

- 原文更新：记录新版本及差异 → 更新本地需求 → 复核范围/验收/依赖 → 评估规格/测试影响 → 必要时重新批准。
- 设计更新：先确认新旧权威关系，再调整 UI 验收；不只改外部链接。
- 决定更新：保留原问题、结论、确认时间和依据，不只删除待确认项。

状态口径：待确认 → 待批准 → 待开发 → 开发中 → 待联调/待验证 → 待验收 → 已验收；另有受阻/已暂停。**完成勾选只与“已验收”一致**；文档、代码、PR 合并或技术 tasks 完成都不能勾产品完成。已验收 ≠ 已上线。重开已验收项时清除勾选并保留旧验收记录。

## 9. 交付检查

- [ ] 需求版本、设计来源、批准依据、规范、现状和进行中变更已核对，未用聊天记忆替代
- [ ] 内容符合文档职责表，业务规则、设计、产品状态、技术清单各有唯一位置
- [ ] 缺项和冲突已原位记录，只暂停依赖部分
- [ ] 原文 ↔ 任务双向覆盖；延期功能未混入首期
- [ ] 数值、时间边界、配额、状态、跨端一致性无遗漏，冲突未被静默解决
- [ ] 涉及 UI 时已完成所选范围的页面/状态—节点—子需求映射
- [ ] 新建的模块卡已在版本任务总览登记入口，项目首页链接到总览
- [ ] 已运行文档规范检查并注明实际覆盖范围：
  ```bash
  python3 "${CLAUDE_PLUGIN_ROOT}/scripts/check_docs.py" --root .
  ```
  它检查 Agent 入口、工程规范、产品文档的本地链接与锚点，以及任务卡必填字段和「待确认」格式；不检查外部链接可访问性和图片内容。项目配置另有文档检查命令时一并运行。
