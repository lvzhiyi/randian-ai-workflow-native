# 双轴代码评审

下文的 `${CLAUDE_PLUGIN_ROOT}` 指当前技能所在的插件根目录。如果它没有被替换成绝对路径（如在 Codex 中），从已加载的 `SKILL.md` 路径向上三级定位，执行命令时直接代入绝对路径。在 Codex 中运行下方命令时，在命令前加 `WORKFLOW_HOST=codex`，以使用 Codex 的本机数据目录。

对一段固定范围的 diff 做两轴评审，两轴分开审、分开报告：

- **Spec**：代码是否忠实实现了需求或规格（缺失、范围蔓延、实现可疑、验收场景缺测试、规格来源不一致）。
- **Standards**：代码是否遵守项目规范和技术栈清单。

分开是为了不让一轴掩盖另一轴：规范全守但做错了需求，或需求做对但破坏了约定，都要被看见。

## 何时评审

| 档位 | 做法 |
| --- | --- |
| 轻量 | 默认不评审；用户要求时只跑 Standards |
| 标准 | 交付前跑一次双轴 |
| 完整 | 每段结束只评审本段 diff；全部完成后对整个分支再跑一次 |

本技能只报告，不修改代码。修复由用户决定；修复后回到 `workflow-core:verify` 跑受影响检查，必要时再评审。

## 1. 确定评审范围

1. 对比点：用户给了提交、分支、tag 或 `HEAD~n` 就用它；没给时用当前分支与基线分支的 merge-base，基线取「工作流配置」的 `review.base_branch`，没配置时用远端默认分支（`git symbolic-ref refs/remotes/origin/HEAD`），仍取不到再问用户。
2. 先确认对比点存在（`git rev-parse <对比点>`）。
3. 范围 = `git diff <对比点>...HEAD` 加上未提交的工作区改动（`git diff HEAD`）；记录提交列表 `git log <对比点>..HEAD --oneline`。
4. 排除生成文件（规则由技术栈插件提供，如 Flutter 的 `*.g.dart`、`*.freezed.dart`）和锁文件以外的二进制资源。
5. 范围为空或对比点无效时立即停止并说明，**不要**启动子代理。

## 2. 找 Spec 来源（命中第一个即停）

1. 用户给出的 change、任务卡、Issue 或文件。
2. 规格工具的变更（如 OpenSpec `openspec/changes/<id>/`）：按分支名、提交信息中的 change-id、任务卡“关联主规格与进行中变更”字段匹配；读 proposal、规格 delta、tasks，有 design 一并读。
3. 任务卡子需求（目录取 `docs.cards_dir`）：读“验收”“当前实现、目标、范围与非目标”“待确认”字段。
4. 交接快照中的“目标与验收”。
5. 都没有时问用户一次；用户确认没有时 Spec 轴跳过，报告写“无规格，Spec 轴未执行”。

多个候选对不上时先确认，不按修改时间猜。命中变更时同时读关联任务卡的验收字段：两者是同一事实的不同记录，diff 只改了其中一处时，Spec 轴要报“规格来源不一致”。

## 3. 汇总 Standards 来源

- `docs.dev_docs` 目录下的规范文件、`code_rules_doc`，以及 `AGENTS.md` / `CLAUDE.md` 中的项目约定（如注释要求、生成代码不手改、不用固定账号代替鉴权）。
- 当前技术栈插件的评审清单（如 `stack-flutter` 的“评审清单”一节）。
- 术语表 `docs.glossary`（配置了时）：新增的类型、枚举、变量和用户可见文案是否使用词条的“代码命名”和术语，是否用了“避免”中的说法。
- [prompts.md](prompts.md) 里的坏味道基线。
- 格式、静态分析等已由工具保证的项不再评审。

## 4. 并行运行两个子代理

本技能明确要求委派：用当前客户端的子代理工具（Codex 的 `spawn_agent` 或 Claude Code 的 Agent）**同时**启动两个子代理，各自从干净上下文开始（不 fork 当前会话），提示词按 [prompts.md](prompts.md) 的模板填写。子代理看不到当前会话，所以模板要求粘贴的内容（规格原文、清单、基线）必须原样贴入。

- Spec 来源缺失时只启动 Standards 子代理。
- 当前环境没有子代理能力时，在本上下文中先完成 Standards 再完成 Spec，报告注明“两轴未隔离”。

## 5. 汇总报告

按下面格式输出，两轴原样或轻度整理，**不合并、不跨轴重排**：

```text
## Spec
来源：<change/卡/文件及版本>
- [阻塞|应修|建议] <问题>｜规格：“<原文引用>”｜位置：<文件:行>

## Standards
来源：<规范文件列表、技术栈清单>
- [阻塞|应修|建议] <问题>｜依据：<文件 + 规则，或“坏味道：<名称>”>｜位置：<文件:行>

汇总：Spec <n> 项（阻塞 <a>），最严重：<一句>；Standards <m> 项（阻塞 <b>），最严重：<一句>
范围：<对比点>..HEAD（+ 工作区），<k> 个文件
```

| 严重度 | 判定 |
| --- | --- |
| 阻塞 | 违反验收或规格的明确要求；安全、鉴权、数据完整性问题；违反技术栈清单或项目规范中**明确标为阻塞**的条目 |
| 应修 | 违反其他成文规范（措辞为“必须 / 不得”的一般规范也归此档）；规格来源之间不一致 |
| 建议 | 坏味道等判断性问题 |

严重度按后果判定，不按规范措辞：注释缺失、硬编码样式值这类规范违反是“应修”，不是“阻塞”。

- 每条问题都要有出处（规格原文或规范条目）和位置；没有出处的推测不报。
- 没有问题就写“未发现问题”，不为凑数编造；坏味道只能是“建议”。
- 复核子代理结论：引用的规格或规范原文不存在、位置对不上的条目删除后再报告。

## 6. 衔接交付

- 交付“验证”项写一行：`AI 评审（Spec/Standards）：<n>/<m> 项，阻塞 <a+b>；范围 <对比点>..HEAD`；跳过的轴写明原因。
- 存在未解决的“阻塞”时，完成状态不能写“可评审”或更高；用户明确接受的例外按 `deliver` 记录。
- 评审结果默认只在会话中；未解决的阻塞项写入任务卡或变更已有的待确认/剩余字段，不新建评审文件。

## 7. 记录度量

报告给用户后写一条度量记录，同一范围重复评审时只记最后一次。`rule` 用报告里的依据（文件 + 规则标题，或“坏味道：<名称>”）；`sources` 列本次实际检查过的规则来源；只写这些字段，不写代码和规格原文。

```bash
python3 "${CLAUDE_PLUGIN_ROOT}/scripts/workflow_metric.py" record review --session "${CLAUDE_SESSION_ID}" <<'JSON'
{"task": "<任务编号或分支>", "tier": "轻量|标准|完整", "files": <文件数>, "sources": ["<规则来源>"], "skipped_axes": [], "findings": [{"axis": "spec|standards", "severity": "阻塞|应修|建议", "rule": "<依据>"}]}
JSON
```

记录失败时按输出修正一次，仍失败就在“剩余”说明；度量不影响评审结论。
