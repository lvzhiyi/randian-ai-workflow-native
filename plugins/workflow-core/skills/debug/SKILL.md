# 复杂故障根因定位

## 何时加载与边界

- **按需加载**：仅在 Bug 调查存在多个可能原因、横跨调用层/缓存/异步链路、难以稳定复现，或 `verify` 判定「原因待定位」「尝试无进展」时使用；常规局部小 Bug 直接按 `tiering` 核对预期、复现与根因，不额外加重流程。
- **遵守门禁**：本技能只负责收窄原因与采证，仍遵守 `workflow` / `tiering` 门禁（未就绪或未授权时只调查采证，不改产品代码）。若项目已叠加 Superpowers `systematic-debugging`，按同一事实与证据边界执行。

## 定位步骤（明确下一步查什么）

1. **锁定预期与复现事实**：记录预期行为、实际现象、触发步骤、复现频率、关键输入与运行环境（配置、缓存状态、版本/数据）。无法稳定复现时，先补最小观测证据（固定输入、时序、日志/抓包）提升复现确定性，禁止凭猜测直接改业务代码。
2. **列假设矩阵，先定判据再动手**：在改代码前写出 2～3 个最可能原因，并为每个假设指定一个可证实或证伪的具体观测点，按信息量最高或排查成本最低的顺序逐一排查。
3. **跨层链路按边界二分采证**：不要一上来深挖单点实现，先沿实际数据流/控制流在关键边界各采一次输入与输出，锁定异常落在哪一段：
   - **调用层边界**：入参构造 → 接口/契约映射 → 领域状态更新 → UI/结果渲染。
   - **缓存与派生状态边界**：缓存键是否含全部决定因子（用户/环境/版本/筛选/分页）、读写时序、失效/刷新是否遗漏或读到陈旧快照。
   - **异步与并发边界**：请求竞态（后发先至）、回调/定时器触发时对象或页面已销毁/切换、重试或重复触发导致副作用叠加、错误被吞或未传播。
4. **单变量验证与及时止损**：一次只验证一个假设，不混改多个变量；观测结果与假设矛盾时立即推翻重排，禁止叠补丁掩盖症状。衔接 `verify`：连续两次尝试无新证据时停止继续试错，先汇总已排除路径与当前边界事实，再重选假设或按 `handoff` 交接。

## 进入修复前的完成标准

修复实施前至少具备以下三项，否则仍处于调查定位阶段：
- **最小复现条件**（或失败用例 / 稳定触发路径）
- **边界证据直接指向的具体根因**（说明为何会发生，而非只看到表象）
- **修复后的回归验证点**（对应原失败场景与受影响边界）
