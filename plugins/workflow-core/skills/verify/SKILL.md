# 验证与失败处理

## 选择检查范围

命令由项目配置和技术栈插件提供，按档位选择，不是每次全跑。

### 改了代码的最低要求（不随档位降低）

只要本次修改了源代码（不含纯文档、纯配置说明），交付前**必须**有以下三项的实际结果：

1. **格式检查**：本次改动的文件
2. **静态分析**：至少覆盖本次改动的文件，有 error 不得交付为“实施完成”
3. **相关测试**：覆盖改动行为的测试；没有可运行的测试时说明原因

命令取用顺序：项目「工作流配置」的验证命令 → 技术栈插件的默认检查（如 `stack-flutter` 的 `flutter_check.py`）→ 技术栈的标准命令。确实无法执行（工具缺失、环境受阻）时按下文分类为“执行受阻”，在交付“验证”项写明原因和影响，**不能省略不提**。

### 按档位扩展

| 档位 | 开发中 | 交付前 |
| --- | --- | --- |
| 纯文档 | 核对关联规则与链接 | `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/check_docs.py"` + 项目配置的文档检查命令；规格产物变化时严格校验对应变更 |
| 轻量代码 | 最小复现或受影响测试；格式化与必要分析 | 定向回归 + 静态分析；纯视觉且无法自动测试时记录交互证据和限制 |
| 标准代码 | 相关测试基线、失败用例、定向回归 | 完整检查一次；UI 变化补实际交互检查 |
| 完整代码 | 按风险选基线，开发中先定向验证 | 完整检查 + 规格严格校验 + 默认平台构建 + 关键链路验收；涉及接口补联调 |

- 新改动、环境变化或未解决的失败才扩大或重复验证；没跑的检查明确列为未验证，不用旧结果宣称当前通过。
- 本地定向检查不替代 CI；Widget/单元测试不等于真机端到端。
- 运行会话存在时用热重载/重启实际检查页面；没有会话时说明未覆盖。
- 只有实际执行过的命令才能写通过；Mock 通过不能写成真实联调通过。

## 失败处理顺序

1. **保留证据**：命令、退出码、关键错误、运行环境、当前变更；先记录再改，不提交含凭据的日志。
2. **确认失败层次**：命令能否启动、检查是否真正执行、结果是否违反验收。缺工具和未运行不能写成失败或通过。
3. **对照基线**：比较同环境、同命令的修改前结果；没有可比证据标“原因待定位”，不直接归为既有失败。
4. **分类并行动**（下表）；一个任务可同时有多个问题，逐项记录。
5. **修复后复验**：先跑最小失败用例，再跑受影响回归；环境变化后重新确认基线。替代验证要说明覆盖差异。
6. **更新状态**：失败仍保持失败；确需外部输入才交接受阻。可独立推进的部分继续。

| 分类 | 判定证据 | 下一步 |
| --- | --- | --- |
| 本次回归 | 基线通过本次失败，或最小复现证明修改引入 | 最小修复并复验；不绕过检查 |
| 环境或工具问题 | 工具缺失、权限、依赖、网络、设备异常阻止验证 | 授权范围内排查或等价替代；需凭据/权限/设备时暂停依赖部分 |
| 既有失败 | 修改前同环境同命令已有相同错误 | 记录与本次变更的关联；相关失败阻塞验收，范围外的单独列出并保持红灯 |
| 原因待定位 | 证据不足以区分 | 继续收集最小复现，不自动宣布无关；无路径时交接 |
| 需求或接口不明确 | 验收冲突、关键字段/错误码/行为未确认 | 汇总问题与影响，等负责人明确；不编造默认业务规则 |
| 超出范围 | 修复需要新能力、破坏性接口或未批准的业务变化 | 说明影响，重新分档确认范围；符合完整档时走提案 |
| 尝试无进展 | 同一方法重复失败，无新证据 | 换假设或验证方法；连续两轮无新证据先总结，仍无路径再交接 |

检查脚本只能区分“未通过”和“执行受阻”，不能判断既有失败或本次回归；因果分类靠证据和人工判断。

## 受阻交接

小任务写在会话或 Issue；复杂任务在对应规格变更或 Issue 维护一份。模板：`${CLAUDE_PLUGIN_ROOT}/templates/blocked.md`。

恢复时重新检查 Git 状态、相关规格和环境，验证恢复条件，重跑原失败命令，再继续依赖任务。状态解除依据实际结果，不依据“已有人处理”的口头结论。
