# 分段实施

## 完整档分段

- 三档均在人工定档/范围确认、完整档额外方案批准、适用基线成功完整读取后实施；任务未就绪只可调查。
- 完整档进入实施后，先按 `tiering` 将已批准的提案与技术设计分别写入 `proposal.md` 和 `design.md`，再按引擎 todo 分段推进。共享底座（网络、会话、鉴权、存储、新依赖）单独一段，业务项按项分段。
- TDD 优先非强制：优先先写失败测试再最小实现，尤其关注鉴权、会话、令牌与持久化边界。不采用时按任务或步骤记录原因和替代验证，再用引擎 `record-tdd` 登记决策；不增加人工豁免审批。
- 每段结束：跑本段定向测试与分析 → 加载 `workflow-core:review`（Claude Code 中调用 Skill 工具）评审本段 diff → 用 `finish-step` 登记已完成步骤 → 更新交接快照（如有）。阶段汇报只写结果、证据和阻塞，必要取舍归入结果或风险，不重复正式交付模板。
- 用户已授权的范围内连续推进下一段，不机械询问“是否继续”，也不把每段汇报变成新的批准门槛。只有风险或范围变化需要用户决策、必要批准未取得、缺少权限或出现真实阻塞时，暂停受影响部分；可独立推进的已授权部分继续。提交、推送、合并、发布仍遵守各自授权边界。
- 移动目录、重命名等结构调整与行为变更**分开进行**。

## 标准档

计划最多 3～5 步，原位写在卡或 Issue 里；已有有效计划直接复用。中途先跑失败用例与定向回归，交付前跑项目配置的标准档检查，再加载 `workflow-core:review`（Claude Code 中调用 Skill 工具） 做一次双轴评审。

原生清单同步与聊天清单降级统一遵守 `workflow` 的「安全同步与聊天降级」规则。

## 三档共同记录

实施 todo 使用稳定 ID，绑定任务、当前轮次和授权摘要；开始时直接使用 `begin` 响应自带的 `progress`（或只读 `progress --task`）同步宿主原生列表，不能只显示 Dashboard。通过实际 CLI `finish-step` 按顺序记录完成摘要（末步可加 `--finish-implementation` 一步进入待验证，响应已内联 `progress`），仅命令成功后再原生同步，失败不勾完成。首未完成步骤切换、失败、恢复、refine-steps 或 repair 后按返回投影或重读 `progress` 重建映射，同轮未变步骤保持稳定 ID，新轮次清除本任务旧映射；不在每次工具调用后刷新、不从 UI 回写引擎。所有步骤结束后仅进入待验证，不等于验证、评审通过或交付。命令先看实际 `--help`，工具参数和无工具聊天清单降级见 `workflow`。

轻量也要实际验证和 Spec + Standards 双轴评审；完整档分段评审不能替代最终整体验证与评审。原范围修复复用授权、新增阶段尝试；范围/验收/实质方案变化按 `tiering` 重新确认。新输入使受影响下游证据失效，不能复用旧通过。返工、取消与恢复保留历史，不用重建任务掩盖失败。

## 减少重复工作

- 产品状态写任务卡，实施进度通过引擎 todo 维护。
- 短计划原位写；当次完成且不受阻的任务不新建交接文件。
- 相同输入、环境、轮次且引擎判定有效的验证证据可复用；输入变化或失败后重跑受影响检查，历史结果只作参考。
- 按当前问题选择适用的辅助技能（调试、TDD、评审等），不把所有技能串成每次必跑的流程。技能额外产物与分档冲突时先说明并协调。
- 复杂根因排查见 `debug`；第三方 API 用法见 `tech-docs`；接口契约见 `api-contract`。

## 文档最小化

- 默认只更新已有任务的实施边界、状态、验收结果、必要证据和未解决问题；不按会话或日期追加“本轮方案”“实施记录”等章节。
- 验证记录只保留代码版本、检查范围、结果、证据位置和未覆盖项；不记命令流水或已解决的环境排错过程。
- 提交、合并、冲突处理、stash 由 Git 追溯，不写进产品文档。
- 同一事实只维护一处：状态和验收归任务卡，设计值与视觉差异归设计索引，架构边界归架构规范；其他位置引用。
- 架构规范只在分层职责、模块依赖、状态归属、生命周期、鉴权或存储等**长期约束**确实改变时更新，修改前先说明哪条约束变了。新增页面、组件、路由本身不是架构变更；不把页面清单、路由枚举、接入进度写进架构规范。
- 其他工程规范（代码、验证、UI、联调等）同样只在长期约定改变时更新；新增功能、接口或测试本身不构成更新理由。写入前先读文件开头的“本文维护 / 不写这里”边界。验证规范只维护检查命令、默认平台和验证口径：单个测试的覆盖场景写在测试文件头注释，验证结果与缺口写在任务卡；不逐个罗列测试。
- 精简文档时把仍有效的内容归回原字段，删除过期表述并修正引用；不把删除过程搬到别处。
- 交付前逐处检查新增记录：是否影响后续实施或验收、是否已有权威位置、是否重复或过期。新增文件或章节必须有现有位置无法承担的明确职责，不能只因技能模板建议而创建。

## 生产代码产物

项目配置或代码规范对注释、命名、生成代码有要求时（如“自定义函数需中文文档注释”），交付前检查本次新增和修改的生产代码；生成文件通过生成源或模板调整，不手改。
