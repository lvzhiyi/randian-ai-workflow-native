# 分段实施

## 完整档分段

- 批准后按 tasks 分段推进：**共享底座**（网络、会话、鉴权、存储、新依赖）单独一段，**业务项每项一段**；不把底座、多个业务项和目录调整合成一次未经检查的大修改。
- 鉴权、会话、令牌、持久化等安全相关逻辑**先写失败测试再实现**；其他段至少先确定测试场景。
- 每段结束：跑本段定向测试与分析 → 加载 `workflow-core:review`（Claude Code 中调用 Skill 工具） 评审本段 diff → 勾选 tasks → 更新交接快照（如有）→ **停下汇报**本段改动、验证结果和本段自行做出的取舍（依赖版本、默认业务规则、提示文案等）以及评审结果，等用户确认是否继续或提交。
- 用户明确授权连续执行多段时可不逐段停顿，但段内验证、tasks、交接照常更新，交付时按段说明改动和取舍。
- 移动目录、重命名等结构调整与行为变更**分开进行**。

## 标准档

计划最多 3～5 步，原位写在卡或 Issue 里；已有有效计划直接复用。中途先跑失败用例与定向回归，交付前跑项目配置的标准档检查，再加载 `workflow-core:review`（Claude Code 中调用 Skill 工具） 做一次双轴评审。

## 减少重复工作

- 产品状态写任务卡；技术清单仅在需要规格变更时写 tasks。
- 短计划原位写，不另建与 design/tasks 重复的计划；当次完成且不受阻的任务不新建交接文件。
- 相同代码和环境已有有效验证结果可复用；有新修改或失败后再跑受影响检查。
- 按当前问题选择适用的辅助技能（调试、TDD、评审等），不把所有技能串成每次必跑的流程。技能额外产物与分档冲突时先说明并协调。
- 第三方 API 用法见 `tech-docs`；接口契约见 `api-contract`。

## 文档最小化

- 默认只更新已有任务的实施边界、状态、验收结果、必要证据和未解决问题；不按会话或日期追加“本轮方案”“实施记录”等章节。
- 验证记录只保留代码版本、检查范围、结果、证据位置和未覆盖项；不记命令流水或已解决的环境排错过程。
- 提交、合并、冲突处理、stash 由 Git 追溯，不写进产品文档。
- 同一事实只维护一处：状态和验收归任务卡，设计值与视觉差异归设计索引，架构边界归架构规范；其他位置引用。
- 架构规范只在分层职责、模块依赖、状态归属、生命周期、鉴权或存储等**长期约束**确实改变时更新，修改前先说明哪条约束变了。新增页面、组件、路由本身不是架构变更；不把页面清单、路由枚举、接入进度写进架构规范。
- 精简文档时把仍有效的内容归回原字段，删除过期表述并修正引用；不把删除过程搬到别处。
- 交付前逐处检查新增记录：是否影响后续实施或验收、是否已有权威位置、是否重复或过期。新增文件或章节必须有现有位置无法承担的明确职责，不能只因技能模板建议而创建。

## 生产代码产物

项目配置或代码规范对注释、命名、生成代码有要求时（如“自定义函数需中文文档注释”），交付前检查本次新增和修改的生产代码；生成文件通过生成源或模板调整，不手改。
