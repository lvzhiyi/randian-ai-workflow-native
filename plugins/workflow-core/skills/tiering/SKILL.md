# 三档分级与最小产物

开工用一句话说明**档位、依据和验证范围**，不为分档另建文档。按风险与不确定性选择，不按代码行数或是否叫 Bug 判断；**完整档条件优先**。

| 档位 | 适用条件 | 执行路径 | 最小记录与批准 |
| --- | --- | --- | --- |
| 轻量 | 文案、文档、局部样式、预期明确且影响局部的小 Bug；不新增能力、不改变业务契约 | 确认预期 → 必要复现 → 最小修改 → 定向验证 → 交付 | 当前会话或已有 Issue；无需 PRD、需求卡、提案、独立计划或交接文件 |
| 标准 | 边界明确的小功能，复用现有架构，影响限于局部模块；无权限、安全、存储迁移或跨系统契约变化 | 需求与验收 → 原位简短计划 → 实现与真实测试 → 相关回归及交付检查 | 在已有需求卡或 Issue 内记录 3～5 步计划和证据；用户明确要求实施且规则清楚时直接推进，无额外提案审批 |
| 完整 | 跨模块协作、新架构、鉴权/权限/安全、持久化或数据迁移、破坏性变更、对外接口契约变化、关键业务规则不确定，或用户明确要求提案 | PRD/需求澄清 → 规格提案 → 必要批准 → 分段实施 → 回归、联调与验收 | 复用或创建 proposal、规格、tasks；有技术取舍再写 design；批准后实施 |

示例 —— 标准：局部表单校验、已有列表的排序或筛选。完整：改登录态契约、接入后台写操作、离线持久化迁移。Bug 若触及完整档风险同样升级。

规格工具按项目配置（如 OpenSpec）；项目没有规格工具时，完整档用项目既定评审机制（Issue / 设计文档 + 评审），**不自行初始化新工具**。项目分档规则优先于规格工具的“所有新功能先提案”通用建议，但完整档仍遵守批准门槛。

## 范围与升级

- 需求卡与规格变更不要求一一对应：一个变更可关联多张卡，一张卡也可复用已有变更的任务。不为凑文件给每张卡重复设计。
- 默认只执行用户选中的范围；跨卡规划或扩大实施范围需明确授权。复用跨卡变更不表示授权执行它的全部任务。
- 标准档发现跨模块影响、契约变化或关键歧义时：保留已完成证据，停止依赖该决定的实现，升级完整档；可独立部分继续。升级不抹掉历史证据。
- 已批准的完整档任务继续复用原变更，不因规则更新而删除提案、重做计划或重置验收。新增范围另行评估。

## 各档执行补充

- **Bug**：先核对既有规格或明确预期，收集复现与根因证据。可自动验证的缺陷先加调用真实实现的回归用例，再最小修复；无法自动复现的设备或视觉问题记录手工操作与限制。
- **标准功能**：在卡或 Issue 内补范围、验收、3～5 步计划和验证方式；无卡时清晰的用户指令加当前会话即可。若改变主规格行为，同步主规格并核对场景与测试，不留过期契约。有进行中变更重叠时先协调。
- **完整功能**：先查现有规格和变更，再准备范围、规格场景、技术任务和必要设计，严格校验并取得批准；依批准范围执行（见 `implement`）。不自动把未验收的变更同步进主规格。用户已批准的同一范围不重复询问。

所有档位：业务需求标为“已验收”需人工明确结论；提交、推送、发布各自依据用户授权，不由档位自动授予。
