# 三档分级

按风险与不确定性而非行数定档，完整档条件优先。先说明建议档位、依据、实施范围与验证范围，取得人工确认并记录来源；不能用 Agent 自报代替。用户已明确确认的同一档位和范围直接复用有效证据，不重复询问。

按 `workflow` 的「在 Agent 窗口定档」展示三档，由用户直接选择。原生单选不可用时，同一聊天里回复档位即可。完整档方案准备好后另请用户批准。

- **轻量**：文案、文档、局部样式、预期明确的局部小 Bug，不新增能力或改变契约。会话/已有 Issue 留目标、范围、验收、来源和至少一项实施 todo；不强制 PRD 或独立计划。
- **标准**：复用架构、边界明确、局部模块的小功能，无权限、安全、迁移或跨系统契约变化。原位 3～5 步短计划与证据；人工定档及范围确认后，无额外方案审批。
- **完整**：跨模块、新架构、鉴权/权限/安全、持久化迁移、破坏性或外部契约变化、关键业务规则不确定，或用户要求提案。先在会话中展示提案、技术设计和实施步骤，再取得人工方案批准。

三档共同路径：任务就绪 → 完整读取适用基线 → 实施 → 规定验证 → Spec + Standards 两轴通过。轻量可压缩记录，不能跳过人工定档、基线、验证或任一评审轴。Agent 终态是“评审通过”，不是自测完成、人工验收或产品交付。

## 完整档提案与设计

- 完整档变更目录为 `<docs.dev_docs>/changes/<task-id>/`，默认 `docs/development/changes/<task-id>/`。新任务使用可作为单个目录名的引擎任务 ID。提交范围供人工确认时，将本任务的变更目录列入引擎 `scope`。
- 请求批准前完成提案与技术设计。提案记录需求来源、目标、范围与非目标、影响、风险、回滚和验收。设计记录实施方式、受影响的模块和关键取舍，按变更内容补充接口、数据或状态流转等细节。
- 将提案及关键设计决策登记到引擎的 `proposal`（设计决策写入 `proposal.design`），将结构化步骤登记到 `steps`，再用该版本请求批准。
- 进入实施后，在修改产品代码前将已批准的提案和设计分别保存为同目录的 `proposal.md` 与 `design.md`，提案链接设计。实施步骤和完成进度由引擎维护，文档按需引用稳定的步骤 ID。
- 续做已有有效批准的任务时，沿用该轮已批准的文档路径和范围，按任务记录定位历史材料。
- 长期有效的业务规则更新到产品需求说明，工程约定更新到相应工程规范。方案发生实质变化时，同步引擎控制字段，按下方规则重新取得批准。

## 授权有效期与变化

- 批准绑定任务当前轮次及控制摘要，有效性看当前范围和证据，不按会话次数或固定时间机械过期。
- 档位、范围、验收或实质方案改变：暂停依赖部分，重新人工确认；完整档重新批准。保留原轮次和证据历史，不把旧授权扩展到新范围。
- 换会话/Agent、原范围修复重试、措辞调整和 todo 细化不新增审批；必要时重读基线、复验，但不重批有效方案。
- 一个变更可关联多张卡，复用变更不等于获准实施全部任务。不为每张卡重复提案。
- Bug 先核对预期、复现与根因（多可能原因或横跨调用层、缓存、异步链路时按需加载 `debug`）。TDD 优先，无法采用时记录原因和替代验证，不增加人工豁免审批。

引擎可能对控制字段保守撤销授权；展示措辞用 `note`，不要为文案调整重写控制字段。真实语义变化与摘要不一致时明确报告，不能假装批准仍有效。CLI 与防护栏边界见 `workflow`。
